# Web and mobile connector development

This branch adds a compatibility test for ordinary ChatGPT and Claude web/mobile
interfaces. It is separate from the working local Circle wallet integration.
The published `naira-offramp-mcp@0.2.2` does not include this development command.

## Current milestone

The test has browser OAuth consent, a Streamable HTTP MCP endpoint, and two tools:

| Tool                       | Purpose                                                                    |
| -------------------------- | -------------------------------------------------------------------------- |
| `get_connection_readiness` | Report the connected client's name and advertised form capability.         |
| `test_human_approval`      | Request a harmless accept/decline form when the client advertises support. |

There is no Circle session, wallet balance, recipient registration, PAJ order
creation or transfer in this server. Even successful test approval leaves payment
execution unavailable. Neither tool accepts credentials or confirmation arguments.

OAuth consent grants access to these public compatibility tools only. It does not
verify a person's identity or wallet ownership. The client supplies its own display
name. All clients, codes, grants and MCP sessions are in bounded process memory;
restarting the server invalidates them. This provider must not authorize real
wallet or payment tools.

## Run from source

Use the existing Node installation and project dependencies:

```sh
npm run check
npm run test:web
npm run web:probe
```

The operator runs this command. End users connect through their chat client's
connector settings and browser consent; they do not run npm or handle test tokens.

After the endpoint is reachable, the operator can check its OAuth/MCP exchange:

```sh
node scripts/smoke-web-probe.mjs https://YOUR_TEST_HOST
```

This uses a synthetic connection, programmatically cancels the sample form, and
revokes its token. It does not verify that a human UI appears in ChatGPT or Claude.

The default listener is `127.0.0.1:8788`. Open `http://127.0.0.1:8788/` for the
connection-test page. The MCP endpoint is `http://127.0.0.1:8788/mcp`.

Web clients need a reachable HTTPS endpoint, supplied by a deployment or an
operator-managed HTTPS tunnel. Set its origin before starting the server:

```sh
OFFRAMP_WEB_PROBE_URL=https://YOUR_TEST_HOST npm run web:probe
```

Configure the deployment/tunnel to forward to port 8788 and preserve its Host
header or use the loopback upstream Host. Use `OFFRAMP_WEB_PROBE_HOST=0.0.0.0`
only when the deployment requires it. `OFFRAMP_WEB_PROBE_PORT` changes the listener
port. HTTPS termination is the deployment's responsibility.

The server accepts requests without an Origin header (server-side MCP clients)
and requests from its own origin. If a browser-based inspector sends its own
Origin, explicitly allow it:

```sh
OFFRAMP_WEB_PROBE_ALLOWED_ORIGINS=http://localhost:6274 npm run web:probe
```

There are no wildcard origins. Non-loopback origins require HTTPS. No Circle,
PAJ or LLM credentials are needed or used. The test does not read `provider.env`,
`service-identity.json`, Circle credentials or existing payout history.

## Test in a real client

1. Add the HTTPS `/mcp` URL as a custom remote connector in the target client.
2. Choose OAuth when prompted. Leave manual client credentials empty to use
   dynamic client registration.
3. Review the browser page and select **Connect test**, or cancel.
4. Ask the agent to call `get_connection_readiness`.
5. Ask it to call `test_human_approval`. Check whether a form actually appears.
6. Test decline and cancel as well as acceptance. A response generated by the
   client is not independent evidence that a human saw the form.

Suggested prompt:

```text
Use the Naira Offramp connection-test connector.
Call get_connection_readiness and report its actual results.
Then call test_human_approval so I can check the human form myself.
Do not infer payment support from a successful test. Do not request
wallet credentials, register recipients, create orders or send funds.
```

The consent page expires after five minutes; authorization codes last one minute.
Each consent attempt has its own short-lived browser cookie, so opening another
attempt does not invalidate an earlier tab. Complete the consent in the same
browser that opened it. A server restart or a previously submitted form requires
a fresh connection from the chat app; refreshing the old form cannot renew it.
The page distinguishes an expired request from a missing or changed browser
cookie without exposing cookie values or authorization details.
The consent page's form policy permits its own origin and that request's
registered callback origin, because browsers can enforce `form-action` again on
the redirect back to the chat app. Other pages allow only their own origin.
The test CLI logs redacted consent lifecycle events and OAuth route/status codes
to help distinguish accepted, repeated, expired and unknown requests. Attempt
references are one-way hashes; logs omit request bodies, headers, OAuth query
parameters, cookies, callback URLs, codes and tokens. These logs and HTTP checks
do not replace observing the complete browser connection flow.
Access tokens last 15 minutes. An `offline_access` grant allows rotating refresh
tokens with a one-hour lifetime. Tokens are scoped to this exact `/mcp` resource.
MCP sessions are bound to their OAuth connection, limited to four per connection
and 64 overall, and expire after 15 minutes of inactivity. MCP requests are limited
to 120 per connection per minute. OAuth endpoints also use the SDK's rate limits.
Revoking a token revokes its connection's access and refresh tokens.

The server implements the authorization-code/PKCE flow using the installed MCP
SDK and dynamic client registration. It does not implement Client ID Metadata
Documents. Compatibility with each target client and protocol version must be
observed rather than assumed.

For each real client test, record the date, client/version, account plan,

codes, OTPs or wallet credentials. Automated protocol tests are separate from
these real-client observations.

## Following milestones

Before enabling web payments:

1. Validate a supported Circle authentication flow that works outside the chat
   sandbox. A separate browser page must collect login credentials and OTPs.
   Connector OAuth is separate from Circle authentication.
2. Choose and implement the wallet-session trust model. The existing PAJ backend
   receives no Circle credentials. Hosting user sessions would change that
   architecture and requires explicit per-user session and storage isolation.
   A local bridge preserves local wallet sessions but requires a running computer.
3. Bind the authenticated connector account to its own wallet, connection identity
   and payout history. Never share the operator's Circle session with users or
   mutate a global process environment to select a user.
4. Validate a real human approval mechanism for each supported client. If native
   forms are unavailable, design an authenticated browser approval flow bound to
   the existing order and complete terms. An agent-generated boolean is not approval.
5. Preserve the existing payout expiry, idempotency, durable submission and
   reconciliation protections. Run controlled integration tests first.

A live payment test needs the user's explicit approval of its concrete recipient
and terms. This milestone does not perform one.

## Consent-page reference lock

Research used Refero styles for [N26](https://n26.com),
[Expo](https://expo.dev), and [Stripe](https://stripe.com), plus the
[Intercom authorization screen](https://refero.design/pages/725f9f07-e8c7-44d9-ab14-56328ae0e815)
and its [integration flow](https://refero.design/flows/683).

Primary direction: N26's white canvas, ink text, teal primary action, flat ledger
dividers and small-radius controls. Borrow Expo's compact content hierarchy and
Intercom's requesting-app, permissions, cancel and authorize sequence. Stripe's
marketing gradients and large display treatments are not used.

| Decision                                                  | Reference or constraint                            | Role                                                                               |
| --------------------------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------- |
| White background, ink text, teal action                   | N26 style                                          | Teal identifies interaction, not decorative backgrounds.                           |
| Single contained column, 4px spacing scale, thin dividers | N26 and Expo                                       | Keep permission details readable before the decision.                              |
| System sans-serif, 16px body, 32px heading                | Intercom screen and mobile readability             | No external font request on a consent page.                                        |
| Visible requesting app and callback origin                | Intercom screen and OAuth boundaries               | Make the connection destination reviewable; label the app name as client-supplied. |
| Equal access to cancel; 48px controls                     | Intercom flow and touch accessibility              | Keep declining practical on small screens.                                         |
| No photography, gradients or animation                    | Expo's functional imagery strategy and narrow task | Keep the permission decision central.                                              |

References informed the page; no external images, fonts or scripts are loaded.
